# Workspace identity gateway and session contract

Status: architecture only, 2026-10-09. No service, dependency, SQL, native or deployment change is authorized by this artifact alone. Implementation follows independent review. Full R08/R09 server/native/provider gates remain open.

## Product and trust decision

Offline library writing, exports and eligible device PCC need no Scriptum account. Offer **Mit Apple anmelden** only when the person chooses cloud sharing or server scheduling. Before Apple authorization, explain the configured server origin/operator, account purpose and transmitted identity proof. Establishing that account does not upload a library or enable scheduling. Library enrollment, sharing and unattended execution each need their own informed action and confirmed server readback.

The initial native identity provider is Sign in with Apple. This is separate from native ChatGPT subscription login, API keys and Apple Private Cloud Compute. None grants Scriptum server identity, unattended provider delegation or billing authority. Server workers require independently verified eligible provider grants and current resource permissions; never copy device ChatGPT/PCC tokens into this gateway. JWT roles, groups, email and client-supplied account IDs confer no Workspace rights.

The backend account key is the exact `(verified issuer, verified subject)` pair already unique in `accounts`. Keep the existing random internal account UUID. Do not merge by email/name, canonicalize subjects, or trust an unverified native `user` string. A future additional issuer gets its own configured profile and separate subjects; linking identities requires fresh proof of both accounts and a reviewed migration. Apple app/team transfer subject migration is an explicit future Apple-supported transfer process, not an email-based merge.

## Actual starting point

`Server/WorkspaceService/sql/001_workspace.sql` has `accounts(identity_issuer, identity_subject)` and `server_sessions(token_digest bytea[32], account_id, expires_at, revoked_at)`. `src/workspace-store.ts` hashes opaque tokens with SHA-256, reads a current session using `FOR SHARE`, then freshly checks session and inherited ACL under the library lock. There is no verified issuer admission or enrollment today. Existing test-created synthetic accounts/sessions are fixtures, never production bootstrap routes. `docs/WORKSPACE_HTTP_PLAN.md` owns the independent HTTP wave and existing `/session/logout`; this document does not rewrite it.

Identity admission reuses that same Pool, schema and transaction helper. It does not instantiate another WorkspaceStore or change the existing document/ACL algorithms. Membership creation remains owner-managed and library-scoped. Authenticating a new account creates no memberships, libraries, schedules, vault keys or provider grants.

These are proposed config names, not claims that values, entitlement or keys are installed.

For the Apple profile the documented fixed issuer is `https://appleid.apple.com`, JWKS `/auth/keys`, token `/auth/token`, revoke `/auth/revoke`, algorithm RS256 for incoming identity tokens. The exact native audience must be the actually enabled App ID/client identifier from deployment provisioning, not a value inferred from this checkout. Team, key ID, private signing key, notification audience, production origin and vault references remain unprovisioned until verified. Outbound Apple client-secret signing uses its separately configured ES256 developer key; this is not an allowed incoming JWT algorithm. A Services ID/web flow requires a separate reviewed profile and exact redirect URI, not adding another audience to the native profile.

Disabled or missing/inconsistent config exposes no working enrollment route and never a development-token fallback. Fail startup identity readiness without dumping values. Limit profiles to 8. Production HTTPS URLs must have exact allowlisted scheme/host/port/path, no userinfo/query/fragment. Do not follow URLs from `iss`, `jku`, `x5u`, discovery data, request DTOs or JWT claims. Do not fetch automatic discovery. Restrict outbound networking to configured identity hosts, disallow redirects, and validate TLS normally. Test-only issuer fixtures use an explicit test configuration with owned HTTPS and trusted test CA; production does not accept HTTP/localhost overrides.

## Proposed wire APIs

Identity routes will use the existing strict HTTP parser, explicit DTOs, no duplicate/unknown keys, fatal UTF-8 and no permissive CORS. No identity proof in URLs, cookies or logs. Responses use `Cache-Control: no-store`; enrollment must never redirect with tokens.

| Route | Input | Outcome |
| --- | --- | --- |
| `POST /identity/challenges` | `{profileID, consentVersion}` only | `{challengeID, challengeSecret, nonce, state, expiresAt}`; exact configured supported profile, consent-version check |
| `POST /identity/enroll` | `{challengeID, challengeSecret, state, identityToken, authorizationCode}` only | `{sessionToken, sessionID, accountID, expiresAt}` after verified proof and atomic DB finalization |
| `GET /session` | opaque Bearer only; no body | current internal account/session IDs and absolute expiry; never subject/email/provider tokens |
| `POST /session/logout` | current opaque Bearer, existing no-body contract | revoke that session; after successful commit subsequent use fails; native clears its credential regardless of network result and explains when remote revocation is unconfirmed |
| `POST /session/logout-all` | opaque Bearer, no body | revoke all account sessions under the account lock |
| `POST /identity/apple/events` | `{payload}` signed Apple event JWT only | verify dedicated notification profile; idempotent processing and controlled acknowledgement |
| `DELETE /account` | session plus fresh reauthentication challenge receipt bound to that account, reviewed retention confirmation | tombstone account, revoke all sessions and queue durable provider-token revocation; preserve owned library data until an explicit retention/export/delete flow succeeds |

Cloud account deletion is not ordinary logout. Native UI must provide account deletion before this login is released. Its data-retention contract needs a separate user-facing review; never silently delete offline libraries or shared collaborators' content. Fresh proof is one-use, at most 5 minutes old and bound to the existing account, not the enrollment endpoint creating another account. This route is an implementation gate, not existing functionality.

## Challenge and replay state machine

Generate independent 32-byte values with Node `randomBytes`: challenge secret, nonce and state; encode canonical unpadded base64url (43 characters). Use a random UUID for the public challenge ID. Store SHA-256 digests of all three, profile ID, consent version and database timestamps; never plaintext challenge secrets or tokens. Native passes the **exact returned nonce** into `ASAuthorizationAppleIDRequest.nonce` and exact state into its request, checks returned state, then sends proof only to the origin that created the challenge. Do not mix raw-nonce and hashed-nonce conventions. The server compares SHA-256 of the token's nonce to the stored digest, with fixed-size timing-safe comparison.

Lifetime 5 minutes; one verifier attempt per challenge. After strict bounded parsing, atomically claim `pending -> verifying` with `WHERE secret_digest=$digest AND expires_at>clock_timestamp()` and a fresh attempt UUID. Concurrent contenders cannot both verify/enroll. No DB connection or lock remains held over JWKS/token/vault network calls. Validated proof is finalized only against that same attempt, before expiry, in one DB transaction that creates/upserts the account, records consent, inserts the session and marks the challenge consumed. Failure consumes that attempt without creating account/session; timeout/crash leaves it unusable and expiry cleanup removes it. The person starts a new challenge. Do not reopen a failed challenge or persist its raw proof for retries.

Consumed/failed records retained 24 hours then pruned. Deleting an old record cannot make its ID usable: enrollment never creates a missing challenge. Bound live/retained records at 100,000 globally; when full reject new challenges with controlled 429/503, not eviction of unexpired records. Implement the capacity check transactionally under a dedicated admission counter/lock shared across replicas. Per origin/rate bucket: challenge 5/minute burst 5, enrollment 10/minute burst 10; 32 concurrent verifications globally. Deployment limiter must use bounded shared storage, not unbounded per-IP maps: at most 100,000 rate buckets, expire idle buckets after 15 minutes, reject new buckets at capacity rather than bypassing limits. Treat proxy client addresses only from explicitly configured trusted proxies; never untrusted forwarded headers.

## Verification and issuer exchange

Pin an audited exact `jose` version and lockfile integrity during implementation; this plan does not add a dependency. Use `jwtVerify` with the configured resolver, exact issuer/audience, algorithms `['RS256']`, required `iss/sub/aud/exp/iat/nonce`, `clockTolerance:60`, `maxTokenAge:'5m'`. Require scalar `aud` equal to the single native audience for this profile, bounded nonempty string `sub`, safe integer numeric dates, expiry after issue time and no future issue beyond tolerance. Issue time must be at least challenge creation minus 60 seconds. Expiry must be valid now; do not interpret an expired token as refresh permission. Reject unsupported critical headers, `none`, HMAC/algorithm confusion, JWE and detached payloads. Require bounded nonempty `kid`; reject `jku/x5u/jwk` rather than honoring them. Pre-parse bounded compact JWT header/payload with duplicate-key rejection, but never treat those unverified values as authority. All claims are checked again after signature verification.

Verify the received identity token before redeeming the one-use Apple authorization code. Send the code only to the configured token endpoint with exact client ID and a vault-signed Apple client secret. Then independently verify the exchanged ID token; require matching issuer, subject and audience. Enforce nonce equality when returned; the originally verified native token must always carry the challenge nonce. Validate grant response shape, TTLs and bounded tokens. Do not create a session on signature success alone when grant redemption fails, returns a different subject, or the vault is unavailable. Returned access/refresh tokens never reach the native app or workspace-session tables.

Store Apple's refresh grant only through a reviewed encrypted vault adapter, with an opaque DB reference and identity/account binding. Enroll fails closed unless that grant can be durably retained for Apple-required revocation/account deletion. Vault write occurs before session finalization; transaction failure leaves only an orphaned opaque grant, which is queued for bounded cleanup/revocation. There is no transaction spanning SQL and the external vault: document and test this compensating lifecycle. Code redemption timeout is uncertain and is not automatically retried; require new interactive proof. No silent local or provider fallback.

## JWKS key rotation and bounded network behavior

One resolver per configured profile using `createRemoteJWKSet`, `timeoutDuration:3000`, `cooldownDuration:30000`, `cacheMaxAge:600000`, and a reviewed `customFetch`. Fetch must retain jose's abort signal/manual redirect behavior, enforce exact configured URL, status 200, response/body deadline and 64 KiB maximum **while streaming**, at most 32 keys, bounded `kid`128 UTF-8 bytes and valid public RSA signing material. Reject private JWK parameters, duplicate/conflicting key IDs and unsupported key types/usage. No token-controlled `.reload()` calls or persisted client-writable key caches.

A missing key can trigger the resolver's bounded rotation fetch after cooldown; at most one in-flight fetch per profile. During cooldown an unknown key fails, not bypasses verification. Valid cached matching keys are usable only inside the 10-minute cache age. Expired cache, fetch timeout, malformed keys or unavailable issuer fail closed with generic controlled unavailable/authentication errors; no stale-forever cache or signature bypass. Identity-token endpoint deadline 5 seconds, 32 KiB response; revocation endpoint 5 seconds. Entire enrollment at most 10 seconds and still bound to challenge expiry. Network failures disclose no endpoint/key/token/body detail.

These timeout/cache values are Scriptum policy decisions, not Apple requirements. Exact current jose source documents its resolver options and custom fetch; a bounded custom fetch is necessary because default JSON parsing does not impose our response-byte limit.

## Opaque session, expiry and revocation policy

Return a newly generated 32-byte random unpadded base64url token once. Store only `sessionDigest(token)` in the existing 32-byte column, never ID tokens, Apple access tokens or clear session tokens. Collision insertion failure regenerates up to 3 times before controlled failure; do not replace someone else's session. Native stores it per exact server origin/profile/account in Keychain with device-only protection and no synchronizable flag. Each scene/library cloud binding references that credential explicitly; no global default account fallback for a different server or library.

Absolute lifetime 8 hours, no sliding extension and no Scriptum refresh token in the first identity wave. `/session` reads expiry, never renews. On expiry native asks for fresh interactive Apple proof before cloud access; offline drafts remain available. Apple vault grant is for revocation/lifecycle, not silent Scriptum enrollment or unattended AI permission. Cap 20 live sessions per account; under account lock revoke oldest session when enrolling the 21st, with opaque event metadata. Retain revoked/expired session rows 30 days then prune safely.

Lock account row before final enrollment, logout-all, account tombstone and issuer revocation processing. Admission checks account active state; future workspace authentication must likewise join/check `disabled_at` or otherwise ensure all sessions are revoked atomically. Existing session `FOR SHARE` ensures same-session logout cannot commit ahead of an already admitted transaction holding that lock. Maintain a documented global lock order (account -> session -> library for paths requiring those locks); review existing WorkspaceStore and logout paths for reverse order/deadlocks before implementation. A concurrent operation committed before revocation remains a valid preceding operation; no retroactive guarantee.

Native observes Apple credential-revoked notification and checks credential state when resuming cloud work. Clear local session and call revoke-all when applicable; network failure is shown honestly. Verify Apple server notifications using separately configured expected audience and fixed Apple resolver, not an enrollment nonce requirement. Use a dedicated notification claim contract rather than reusing enrollment-required claims: require issuer, configured notification audience and finite integer iat, reject issue times over 60 seconds ahead or over 24 hours old; validate exp when present, without assuming Apple notification tokens always contain it. Strictly parse the documented signed events representation with bounded subject/type/event time; it must never select another issuer. Deduplicate the exact signed token digest (and verified jti when present). Retain event digests for 25 hours after receipt so cleanup cannot reopen the 24-hour acceptance window, maximum 100,000; reject beyond capacity rather than processing unverifiable/replay-ambiguous data. `consent-revoked`/`account-delete` disable the matching issuer+subject account and revoke its sessions in one transaction. A later verified interactive enrollment can reactivate consent-revoked accounts only under a reviewed explicit consent transition; deletion tombstones cannot be silently recreated. Email forwarding events do not alter roles or auto-delete data.

Issuer notifications and native checks reduce revocation delay; the service cannot claim instantaneous knowledge of an issuer event not delivered. Absolute expiry bounds otherwise valid sessions. Session logout does not implicitly cancel previously authorized server tasks or revoke an API-provider grant: the cloud logout UI must state that and offer the separate pause/cancel/revoke actions before logout. Workers always freshly check account status, ACL and independent grants; revoked/disabled account means no new dispatch.

## Permanent real HTTP/PostgreSQL proof

Use the existing explicitly opted-in dedicated PG18 verification database and unique advisory-locked test schemas. Keep existing SQL/HTTP suites unchanged; no skipped database tests count as PASS. A locally owned HTTPS issuer fixture signs actual JWTs with real test keys and exposes bounded JWKS/token/revoke endpoints. It tests crypto and real network behavior, not Apple production authorization. Separate live Apple/native proof still required.

1. Execute migration twice, restart service; preserve old account/library/page/history bytes. Wrong checksum and malformed legacy subject roll back without partial columns/data. Legacy production sessions revoked deliberately, never silently trusted.
2. Actual challenge -> signed native ID token + matching code exchange -> real account/session commit -> actual encrypted page ACL read/write. DB contains only token digests/vault references; captured HTTP/server/SQL logs contain none of token/email/subject/code/secret/ciphertext.
3. Invalid signature/key/algorithm, wrong issuer/audience/subject, duplicate claims/header fields, missing/expired/future dates, missing/wrong nonce/state/secret, mismatched exchanged subject and unknown profile deny without new account/session or page/history mutation.
4. Two real concurrent enrollment clients for one challenge produce exactly one session; failure/crash/restart/expired challenge cannot replay. Same issuer+subject concurrent independent challenges converge to one account; equal subjects under different issuers remain distinct; email equality never merges.
5. Key rotation A->B through real HTTPS JWKS, cooldown unknown-kid flooding, concurrent resolver fetch sharing, expired cache, slow/no response, redirect, oversized streamed/chunked JWKS, bad TLS, duplicate keys and malicious jku/x5u never bypass. Assert no request reaches attacker-provided URL.

8. DB failure during final session commit produces no consumed-success/account/session partial state; verifier attempt remains non-replayable. 9. Signed lifecycle event duplicates handled once, same-sub different issuer isolated, forged/wrong-audience/oversized/expired notifications denied. 10. Strict 24 KiB enrollment body, 8 KiB headers, 16 KiB JWT total, decoded header <=1 KiB, decoded claims <=8 KiB, code <=4 KiB, subject/issuer <=256 UTF-8 bytes, challenge canonical lengths.
