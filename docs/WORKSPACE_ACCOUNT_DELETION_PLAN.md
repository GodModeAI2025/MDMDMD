# Native account deletion contract for review

Docs-only proposal against coordinator `5281578`. No source/UI/portal changes. Existing restore/login/logout and all 15 coordinator assertions remain intact. Deletion does not remove local Markdown, attachments, histories, binding metadata or owned/shared server libraries. UI must explain the server's `preserve-owned-libraries` retention contract and obtain a deliberate confirmation before calling this API; a boolean from the UI is never server authorization.

## Exact proposed APIs

- Coordinator: `deleteAccount(windowID: UUID, scope: WorkspaceAccountScope) async -> WorkspaceAccountDeletionResult`; `cancelAccountDeletion(windowID: UUID)`; `retryDeletionLocalCleanup(scope:) async`. Result enum contains only controlled outcomes: cancelled, superseded, wrongAccount, authenticationUnavailable, localPersistenceUnavailable, confirmedAccountTombstone, remoteDeletionUnknown. No credential/receipt field.
- Extend internal driver: `deleteFreshEnrollment() async throws -> WorkspaceAccountDeletionOutcome`. It uses only its retained real WorkspaceIdentityEnrollment.reauthenticationReceipt and actual WorkspaceIdentityClient.deleteAccount(using:). There is no receipt parameter exposed to coordinator/UI, no synthesized receipt and no Keychain save during deletion. The existing gate protects challenge/proof/enrollment cancellation; issued-session cleanup still uses real discardIssuedSession.
- Extend admission boundary from logout boolean to typed reason (localLogout/logoutAll/accountDeletion/unauthorized), preserving old callers and exact ticket CAS. Production deletion commits actual `.accountDeletion` denial.
- Add controlled presentation states `reauthenticatingForDeletion(scope:attemptID:)` and `deleting(scope:)`; final existing `localDenied(scope:remoteOutcome:)` distinguishes confirmedAccountTombstone/deletionUnknown. Pre-fence failures report a result and restore previous presentation only if its slot generation still matches; they never revive a replaced session.

## Ownership, transitions and ordering

Deletion attempt is a separate bounded container (combined login+delete attempts <=8, windows/slots <=64). It captures exact target scope, slot incarnation/generation and requesting window from the start, plus a new independent identity driver. Require window currently attached to that scope; no default-account or library selection. Do not rotate the active slot generation merely to start reauthentication: original active A driver remains usable until proof succeeds and deletion fence commits. Another account B remains intact.

1. Retain the target slot with a pending-operation count; allocate exact deletion attempt ID and independent proof-bound driver. Challenge -> actual Apple proof -> code-redeemed server enrollment. Recheck own attempt ID, scene ownership, target slot generation, Task cancellation and exact deployment after every await. Logout A/scene detach/cancel consume this attempt and synchronously close its proof gate. Logout B does not cancel a known-target A deletion attempt or rotate its target generation.
2. Validate enrolled account equals target A before any local denial, Keychain operation, connection invalidation or DELETE. Wrong B response: revoke only the newly issued B session via that independent driver; preserve A's original driver/Keychain/handles and any existing B sessions. Unknown targeted cleanup is reported honestly without substituting logout-all.
3. Once exact fresh A is verified, synchronously claim a per-scope destructive-operation reservation, rotate A slot generation, fence all A windows/connection handles/queued matching or account-unknown login attempts and clear prior receipts. Capture the exact current admission ticket and commit durable `.accountDeletion` denial before the first suspension. Preserve the fresh deletion driver and original driver privately; do not invalidate the fresh initiating actor before its delete API captures credential/receipt. No enrollment save/beginExplicitEnrollment/marker-clear occurs in this flow.
4. The reservation rejects matching A restore or new-login *admission* while the deletion start/in-flight lifecycle owns A; an unknown login that later verifies A is discarded without save. B admissions remain allowed. This closes the MainActor→identity-actor suspension window: a new A session cannot be admitted between the synchronous fence and old DELETE start. A login admitted before verification rotates A generation, causing the stale deletion attempt to stop before any denial/DELETE. Once a remote request was sent, cancellation cannot promise to undo server processing.
5. Await exact fresh driver's real deleteFreshEnrollment (one-use, at most the client's conservative five-minute monotonic receipt lifetime). Invoke it once only. Server-confirmed204 -> confirmedAccountTombstone; error/transport ambiguity -> remoteDeletionUnknown. In both cases remove only the exact locally denied credential under returned denial ticket CAS. No stale cleanup may delete a later account's token or override newer presentation. Keep durable denial after removal; no silent cold restore.
6. Final matching A presentation is localDenied with confirmed tombstone or deletionUnknown. Original active driver's local admission is invalidated after the fence, independently of fresh deletion driver. A remote-unknown destructive outcome remains locally denied; do not auto-retry DELETE or claim that cancellation restored the account. A later explicit authentication requires a new server-verification flow and clear disclosure that an already sent deletion may have completed; production UI/status reconciliation is a release gate, not an invented account-status endpoint.

## Failure and cancellation cleanup

Before durable fence: cancellation/supersession/wrong account cleans up only the independent newly issued session and leaves original A untouched. After durable fence: account remains locally denied even if scene closes, receipt expires or network fails. Every terminal post-fence path must perform bounded targeted discard of the independently issued fresh session, including cancellation/destructive-latch rejection before DELETE starts and wrong-scope, expired or consumed receipt claim failure before the identity client invalidates that session. Exact local denial/removal still completes or remains in controlled retry state; original A stays denied. Target only the fresh returned credential, never an older A session, newer login or existing B session. Track fresh-session cleanup confirmed/unknown separately from account-deletion confirmed/unknown; unknown cleanup cannot be reported as confirmed account deletion or revocation. Once DELETE was sent, targeted discard remains harmless/idempotent cleanup and cannot undo tombstoning. Cancel prevents a not-yet-started DELETE via the per-driver proof/destructive latch; cancellation after request start reports unknown, never rollback success. Own attempt terminal cleanup compares attemptID, preserving a replacement same-window operation.

Durable-denial persistence failure: publish localPersistenceUnavailable, retain a bounded typed cleanup record containing exact target scope/incarnation/generation, fresh driver and original driver, plus current failed admission ticket. Do not lose the fresh receipt by invalidating/discarding the driver immediately. The destructive reservation remains closed until controlled cleanup resolves. `retryDeletionLocalCleanup` retries durable denial and exact Keychain removal only, never automatically sends DELETE. It then targeted-revokes the retained fresh issued session and invalidates original local admission; outcome reports local cleanup and remote cleanup unknown separately. A user who still wants deletion starts a new confirmed fresh reauthentication after cleanup; no expired receipt reuse or surprise later destructive retry. If persistence cannot be repaired, retain honest unavailable state and bounded cleanup data; no silent restoration on restart. Durable-marker/cold-restart guarantees remain those of the reviewed admission module (failure cannot fabricate durable success).

Local removal failure after DELETE: keep the committed denial ticket and controlled cleanup record, retry exact local removal only. Remote confirmed/unknown result is retained as metadata so a retry does not resend deletion or downgrade a confirmed response. Capacity overflow refuses new attempts rather than evicting unresolved cleanup/denial.

## Permanent test matrix before implementation

1. Correct A: fresh independent challenge/enrollment; no save; all A windows/handles fenced and durable accountDeletion denial before DELETE barrier; retained libraries/document bytes unchanged; confirmed and unknown outcomes distinct.
2. Wrong B enrollment: no A denial/remove/DELETE; targeted B-issued-session discard only; existing active A and B unaffected.
3. Cancel while challenge/proof/enrollment awaits: production cancellation gate prevents late prompt/DELETE; returned issued session cleaned up; old attempt never removes replacement same-window attempt.
4. Logout B during A proof leaves A attempt valid; logout A cancels it. Closing requesting window cancels exactly its deletion attempt.
5. Fresh A login wins before deletion proof returns: stale delete does no denial/DELETE. Delete fence wins first: same-A login cannot save/admit while reservation pending, B login remains admitted. No old DELETE starts after newer A admission.
6. Denial persistence failure retains both drivers and cleanup ticket; controlled retry does durable local cleanup + targeted revoke without DELETE; receipt expiration/restart cannot silently reuse it. A new explicit attempt requires fresh enrollment.
7. DELETE unknown or confirmed followed by Keychain-remove failure: denial survives, retry uses exact ticket, never resends DELETE; stale CAS cannot remove a newer token.
8. Actual post-fence barriers: cancel after durable denial but before DELETE invocation, and hold until real receipt monotonic expiry before claim. Assert no DELETE started, bounded targeted fresh-session discard attempted (confirmed and unknown cases), original A remains locally denied, exact Keychain cleanup completes/retries, and existing B/newer-session bytes unchanged. Receipt wrong scope/expired/consumed rejected by actual IdentityClient; driver never exports receipt or persists it. Existing signed HTTPS/PG client tests retained; add actual configured-driver deletion fixture before release.
9. Bounded repeated cancel/close/capacity tests retain live/pending cleanup incarnations, free terminal attempts and never leak signingIn/deleting state.

Native deletion UI, actual Apple authorization, deployed operator/TLS/vault, physical device and ambiguous-remote deletion reconciliation remain explicit release gates. This API wave alone does not enable login UI or complete R08/R09.
