# Failed disconnect persistence — process fence

The stored connection selection remains enabled if a disconnect cannot commit its atomic disabled record. Previously, a failed session with no transport could resume that old selection on a later foreground callback, contradicting the message that the connection was stopped for the current session.

Disconnect now sets a process-local blocked intent and fresh revision before attempting IO. The key includes the standardized owned support-directory path and stable library UUID. New descriptor/session objects in that same namespace see the block, while another library or support root stays independent. Automatic restoration checks the block before selection read/account lookup. Each activation captures an intent revision and rechecks it before transport creation and after native activation; an in-flight old activation cannot win after a failed disconnect write, even if the old on-disk selection is unchanged.

Only a fresh explicit activation with the current intent and a successful owned atomic selection write clears the process block. A failed enable write leaves it blocked. A successful disk disconnect also retains the block until explicit enable. This is local application intent, not a server grant or credential. The in-memory fence is intentionally process-lifetime; if persistence failed and the process is terminated, the existing user-visible warning about the next-start selection remains material. No cross-process or real CloudKit proof is claimed.

The new test uses real owned metadata and manuscript files, then injects CocoaError.fileWriteOutOfSpace at the pre-write failure boundary. The injected hook cannot replace successful storage: every nonthrowing path still performs the real bounded atomic write. The test proves old metadata bytes remain enabled/unchanged, stale confirmation/enable fail, a newly constructed session performs zero account lookups, a failed explicit enable keeps the block, a successful explicit atomic enable clears it, independent namespaces remain unblocked and the manuscript remains byte-identical. This is deterministic IO-failure simulation, not a physical disk-full/fsync experiment.

The full suite reports 456 Swift Testing tests (three optional tests skipped) and 58 XCTest tests without failures. Xcode MCP and optimized unsigned Release receipts are recorded separately. Only model/failure logic changed, so no new native layout claim or fabricated cloud grant is added. The source provisioned gate, portal capabilities, profiles and TestFlight distribution remain unchanged; real network/physical-device behavior is still a separate acceptance gate.
