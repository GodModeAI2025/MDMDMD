# R09 — Persistent authorized scheduled work

## Outcome and current boundary

A person schedules a task for a Space/page, chooses its exact readable context, provider, recurrence, spending limits and permitted result action, and can inspect/cancel its persistent runs. A deployed server executes eligible tasks while every Apple device is offline. Results are revision-bound proposals by default; accepting a proposal remains an explicit, source-preserving editor transaction. Client timers, BGTask refresh, notifications and a successful local queue test do not satisfy server execution.

Current source has LibraryStore durable revisions/edit journals, immutable page/block UUIDs, PagePatch allowedBlockIDs + baseRevision checks, scoped assistant context and native provider adapters. It has no deployed scheduling backend, backend identity/role authority, durable remote queue or server provider credentials. Standalone collaboration still has untrusted decoder gates; scheduling must not expose that decoder as an alternative ingestion path. Server receives bounded validated authorized snapshots through its eventual R08 service, not an arbitrary Automerge upload.

## First implementation wave: pure domain plus durable local contracts

Create a standalone Swift module `Modules/SkriptumScheduling` first, with no native project mutation or network behavior. Foundation-only values permit real deterministic tests before server/framework selection. Persisted schema1 JSON describes configured intent and ledger; it must contain no API key, ChatGPT token, page content, raw authorization bearer or PCC entitlement.

- `ScheduledTask`: UUID, ownerAccountID, libraryID, spaceID, targetPageID, generation, rule, prompt, contextScope, providerBindingID, actionPolicy, budgetPolicy, lifecycle, created/modified timestamps. ContextScope explicitly lists readable page/block IDs; server still checks effective access at execution. Prompt/context changes increment generation. Invalid/stale generations cannot reactivate cancelled schedules.
- `ScheduleRule`: oneShot UTC instant or recurring calendar rule with IANA timezone, local time, selected weekdays/day-of-month, optional end/count. First wave supports one-shot and daily/weekly rules, retaining versioned rule extensibility for monthly rules. Later monthly rule is required before claiming complete professional recurrence. DST policy is explicit: nonexistent local time uses the next valid instant on that date; repeated local time executes first occurrence only. `OccurrenceID(taskID,generation,scheduledUTC)` is stable. Inject clock/calendar and reject unsupported rules instead of guessing.
- `TaskLifecycle`: draft, awaitingActivation, active, paused, cancelled. Paused resumes only by explicit authenticated action; cancelled generation is terminal. Failed backend activation stays awaitingActivation with an error, never displays active. Next occurrence is computed from persisted rule/last occurrence, not notification timing.
- `ScheduledRun`: UUID/OccurrenceID, task generation, state, attempts, lease owner/expiry, reservationID, provider request reference, cancellation generation, timestamps and structured failure. States: queued → leased → authorized → reserved → dispatching → running → proposalReady/completed. Distinct cancelled, denied, budgetDenied, failed and executionUncertain outcomes. Legal transitions are validated; attempts cannot fabricate finished/charged outcomes.
- `ExecutionGrant`: server-issued grant identity/version, account/library/Space/task/generation, effective readable resources, eligible operation and expiry. Pure admission checks compare the complete scope and current role result; native stored grants are advisory until server verification. Owner can manage schedules/budgets; editor may schedule proposal-only work only if owner delegation allows; viewer may read authorized result metadata but cannot execute/write. No client bool creates a role.
- `BudgetPolicy` and `BudgetLedger`: integer token ceilings, per-run/monthly amount ceilings in explicitly named currency/micro-units, reservation, settlement and release records. No floating point money. All arithmetic checked for overflow/nonnegative values. Idempotent reserve/settle/release keyed by run+reservation. Open/uncertain calls keep reservations; no blind refund or duplicate reserve. Input/output/context caps are enforced before dispatch. Cost quotes are versioned upper bounds supplied by backend configuration; absent/stale pricing prevents activation of money-limited execution.
- `ScheduledProposal`: UUID, runID, owner/library/Space/page identities, captured baseRevision, allowedBlockIDs, source digest, proposed PagePatch or read-only summary, provider/model provenance and creation/expiry. No direct destructive task action in first wave. Proposal cannot manufacture allowedBlockIDs outside captured scope. Source digest covers exact UTF8 (CRLF/canonical Unicode distinction), not a normalized String hash.
- `SchedulingStore`: actor owns versioned persisted domain state, validates decoded state and invariants, writes a candidate atomically before publishing it, preserves last valid state on write failure, and exposes immutable snapshots. File-based local durable intent/ledger is first-wave evidence only. It does not provide distributed queue claims. Inject persistence adapter and clock, bound record/string/count sizes, reject unsupported schema, avoid plaintext source/secret logs, and keep library/account partitions explicit.

Concrete first-wave files: `Sources/SkriptumScheduling/{ScheduleModels,ScheduleRule,RunStateMachine,BudgetLedger,ScheduledProposal,SchedulingStore,FileSchedulingPersistence}.swift`, matching tests under `Tests/SkriptumSchedulingTests`. Initial hard ceilings: 1,000 tasks, 10,000 retained runs, 1,000 pending proposals, 16KiB UTF8 prompt, 2MiB captured source/context and 1MiB structured provider output per run; entire local scheduler state file32MiB maximum. Bounds are validated before decode/allocation where feasible (file byte check before JSONDecoder) and before persistence. Exceeding retention caps requires explicit pruning policy; no silent dropping of active reservations/proposals. The executable/backend worker is a following separate target, not hidden inside the native app.

Library identity: current WritingLibrary.libraryIdentity is a window/session UUID, not a durable scheduling identity. Bind an authenticated server library ID to the existing persistent owned-library namespace (primary Chats or imported ScriptumLibraries/UUID-derived scope) and account. Do not derive authority from page/Space UUID: imported packages legitimately retain those UUIDs. An import receives a fresh local namespace and no inherited remote scheduling binding/credentials/task activation, even if its metadata contains a copied server ID. Scope binding survives owned container relocation but requires verified server registration. Runtime facades remain isolated.

First-wave API shape: `SchedulerStateMachine.activate(task:verifiedGrant:now:)`, `enqueueDue(now:)`, `claim(runID:lease:now:)`, `reserve(runID:quote:)`, `recordDispatch`, `recordProviderCompletion`, `recordProposal`, `cancel(taskID:expectedGeneration:)`; store `transact(expectedVersion:operation:)` commits validated candidate or returns conflict. Pure values contain execution policy; no provider/network request is issued by a state transition. Root must review the exact APIs/tests before binding them to the app.

### First-wave permanent tests

1. Codable valid roundtrip; unknown schema/rule/state, invalid bounds and forbidden transitions rejected without replacing prior disk state.
2. Restart loads tasks, leases, budget holds and pending proposals exactly; injected atomic-write failure leaves memory and prior disk bytes intact.
3. Clock-advanced enqueue generates one occurrence once, repeated calls/restarts do not duplicate it; generation change isolates old queued runs. One-shot/daily/weekly boundary, timezone change, DST gap/overlap and end condition cases.
4. Concurrent actor callers reserve the final available budget once; overflow, token/currency mismatch, duplicate settlement and release after uncertain dispatch cannot grant funds.
5. Lease expiry permits recovery before dispatch; old worker fencing token cannot write state after a new claim. After ambiguous dispatch, run becomes executionUncertain rather than transparently reissuing paid work.
6. Cancellation before dispatch prevents provider invocation; cancellation during execution prevents proposal/apply publication even if a late provider callback arrives. Repeated cancel is idempotent; completed results remain auditable.
7. Current server-authoritative grant/roles deny wrong account/library/Space, expired/revoked access, forbidden reference scope and viewer write; role inheritance is a server integration gate, not mocked production proof.
8. Proposals reject wrong page/revision/block ID, exact source-byte digest mismatch and duplicate acceptance; read-only summary cannot be interpreted as a mutation.
9. Same page UUID in two libraries never shares schedules, budget authorization or proposals. Recovery/history records do not silently widen current readable scope.
10. Retention/export/delete-account operations contain no provider credentials; logs contain IDs/outcomes but no page/prompt content by default.

## Server execution wave: required for R09 completion

Implement an authenticated scheduling service and separate worker with transactional durable database rows for tasks, occurrence uniqueness, runs, fenced leases, reservations, proposals and audit events. PostgreSQL transaction/unique constraints are the intended persistence model; actual server framework, hosting region and identity provider must be selected/configured in the backend wave rather than inventing credentials here. Queue wakeups are hints; database due records are truth. Polling sweeper recovers missed wakeups and expired leases. Worker startup reconciles uncertain executions; it never assumes a crash means a provider was not charged.

Activation request includes client intent version and idempotency key. Server verifies current account session and effective R08 permissions, provider binding, region policy and budgets, writes active state and returns authoritative task generation/next occurrence. Native UI shows active only after server readback. Worker rechecks grants/roles before loading content, dispatching and recording a proposal; revoked resources are excluded or run denied, never read under an old cached grant. Cancellation increments server cancellation/fencing generation transactionally; late workers cannot publish. Provider cancellation is best effort and may still incur real cost; ledger records actual/uncertain charge separately from user-facing task cancellation.

Execution is at-least-once claimed work with idempotent internal state, not a promised exactly-once external AI call. If provider supports a verified request-idempotency mechanism use it with the run ID; otherwise do not retry after ambiguous network dispatch without reconciliation or explicit owner retry acknowledging possible cost. Each retry reserves eligible additional worst-case spend, respects capped attempts/backoff and remains visible. Task catch-up policy is one latest eligible occurrence with missed occurrences recorded; no mass backlog of paid runs after downtime unless explicitly selected and budgeted.

Capture immutable authorized page/block snapshots and exact revision/digest at execution. Prompt uses the same explicit target/reference/rules scope as native assistant, with bounded token estimation; context truncation is explicit and recorded. Treat document instructions as content, never as authority to widen scope, call other providers or publish. Output parser validates bounded structured proposals; raw generated text cannot trigger an external action. Store encrypted content/proposals in the selected region under server retention policy; audit identifies reads and actions without logging content. Roles/admin debugging do not implicitly expose private drafts.

## Provider and privacy activation paths

OpenAI/Anthropic API-key server work requires explicit separate server credential enrollment (or an owner-funded service binding). Existing device Keychain keys are not uploaded by enabling a schedule. Binding holds an opaque vault secret reference, account/region/provider/model permissions and limits. Server encrypts secrets, isolates tenants, denies redirects/unconfigured endpoints, rotates/revokes credentials and never returns secrets to clients.

Current ChatGPT subscription adapter authenticates a native user session. That is not evidence of permitted unattended server execution/credential delegation. ChatGPT-backed schedule activation remains unavailable until an official eligible server authorization path and terms are verified in that implementation wave; never repurpose device tokens or silently switch to paid API keys. Existing Apple PCC adapter runs through Apple framework/device provisioning. There is no implemented generic unattended server PCC route. PCC-only users can save local intent and run explicitly on an eligible device, with honest device-dependent status; the app must not label that server-guaranteed scheduling or fallback to OpenAI/Anthropic. Full R09 server mode can activate only an actually eligible provider. These capability gates preserve PCC privacy rather than falsifying provider parity.

Task creation/settings exposes scope, recurrence/timezone, provider eligible for selected execution mode, per-run/monthly caps, proposal-only action and retention. User may cancel/pause/view run history even after provider credential loss. Optional APNs is a user-enabled result alert, not execution authority; no email/blog/publication occurs implicitly. Website/blog publishing stays an explicitly authorized later connector action with destination-specific credentials, a reviewable output and approval policy; this plan does not grant publication permission.

## Native proposal application and server proof

Native schedule manager reads server authoritative task/run status and locally persists pending authorized intent across offline restart. An offline create/cancel is shown pending sync; cancellation is not claimed remotely effective until confirmed. Proposal detail presents target revision, diff, consumed/held budget, captured context and provider. Before acceptance finalize the real editor journal/navigation gate, reload the owning library, compare exact current revision/digest and authorized block scope, then use Core's validated PagePatch atomic transaction. Conflict creates an explicit review/rebase path; never overwrite changed drafts. Acceptance must commit a proposal-specific receipt WITH the document mutation in the same owning-store transaction; writing the receipt after Core.apply introduces a crash window and is not accepted. Extend the document persistence schema/transaction in an explicitly reviewed Core wave so restart can read an applied receipt and return the same outcome without applying again. Server acceptance acknowledgement is separately idempotent; retry after an acknowledgement loss consults the durable receipt. Existing process-local LibraryStore/edit-journal state is not distributed/cross-process authority. Never instantiate a second store against the same directory to bypass an active edit or write from a scheduler actor: use the current owning WritingLibrary/store gate and its transaction, with explicit active-edit and trashed-target rejection. The current Core patch-trash rejection is under regression repair and must be verified before integration. Successful local application is distinct from server acknowledgement. Summary is inserted/copied only on explicit choice.

Completion gates: deployed TLS endpoint/identity/vault/region configured; real server-role inheritance readback; durable restart/lease-loss tests; offline native device while server runs a scheduled occurrence; real eligible provider calls within enforced caps; genuine revocation/cancellation race; server outage/catch-up/uncertain billing proof; revision-conflict native proposal handling; push opt-in proof; two-library isolation and account deletion/retention proof. Source/domain tests, localhost workers, simulated providers and UI screenshots alone do not close these gates. No hosting/issuer/secret was provisioned by this plan.
