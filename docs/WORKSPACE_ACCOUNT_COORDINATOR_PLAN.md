# Native workspace account coordinator implementation plan

Status: independently reviewed implementation plan; no native account activation implemented by this plan. Backend `975af95` has independent 53-test evidence. Deployment, production Apple identity configuration, TLS/operator disclosure and production vault remain separate prerequisites. R08/R09 remain open.

## Existing contracts and required boundaries

`WritingLibrary.ownedWindowLocator()` selects an owned persistent library; runtime `libraryIdentity` is not a credential selector. Its document/support roots are private. Add an internal repository factory on the facade using those actual roots, rather than reconstructing paths from page/library UUIDs. At app composition, canonicalize only trusted Foundation system-container roots (including the iOS `/var/mobile` to `/private/var` alias) before constructing owning library and support repositories; use the same canonical roots consistently for locator derivation. Do not resolve arbitrary user-selected library paths or weaken descriptor no-follow checks. Record actual simulator and physical-container path evidence before changing Core; private/tmp tests alone cannot establish the iOS boundary works. `CloudLibraryBindingRepository` already provides bounded canonical nonsecret metadata and process-local CAS. `CloudConnectionRegistry` supplies synchronous MainActor tickets, completion and exact origin/profile/account invalidation; it neither authenticates nor owns clients. Its weak/prunable slots are not durable logout tombstones.

`WorkspaceKeychainCredentialStore` currently has exact profile-scoped load/save/remove, device-only unlocked non-synchronizing credentials, but no epoch admission. A queued save can run after remove. App-only generation checks before an awaited save do not close this gap. The credential-store module needs a coordinated fencing API before login is exposed.

`WorkspaceIdentityClient` owns challenge/enrollment/current-session admission and targeted cleanup of parsed cancelled/superseded enrollments. `logoutAll()` and `deleteAccount(using:)` capture their credential and invalidate internally before network. Calling `invalidateLocally()` first destroys the credential needed for remote revocation. Preserve the initiating actor for its revocation method; fence all UI/data admission synchronously first and invalidate other actor instances asynchronously. `WorkspaceAppleAuthorization` acquires proof only, with the actual scene anchor, state/nonce and cancellation gate.

## Proposed ownership and APIs

New `WorkspaceDeploymentConfiguration` is immutable and injected at app composition: exact validated HTTPS origin, profile ID, consent version, operator name, privacy/service information and configured availability. No inferred host, environment fallback, development token or arbitrary user-entered issuer. Missing provisioning yields unavailable cloud controls; offline writing stays available.

New process-shared `@MainActor WorkspaceAccountCoordinator` owns bounded account slots keyed by exact canonical origin + exact profile + account UUID, plus bounded provisional login attempts keyed by deployment and attempt UUID. Each account slot has generation, state, identity client, admitted credential scope, weak scene/library subscribers and cancellation tasks. A per-library facade holds an exact owned locator and current registry handle. The window registry remains responsible for library lifetime, not account discovery. No default account, Keychain enumeration or automatic account switching. Every account-unknown provisional attempt owns a distinct identity actor, never an already active account actor.

Proposed coordinator entry points: `restore(library:)`, `signIn(library:anchor:)`, `cancelSignIn(attemptID:)`, `logout(accountScope:)`, `logoutAll(accountScope:)`, `deleteAccount(accountScope:receipt:)`, and explicit `connectLibrary(library:remoteLibraryID:)`. Return controlled presentation states/outcomes; never expose token, Apple proof or receipt in descriptions. All admission uses captured deployment, account generation, locator and attempt IDs. Library connection requires authenticated remote readback and a registry ticket/CAS; sign-in alone does not upload, create remote content or grant sharing rights.

## Credential fencing and durable denial

Coordinate a narrowly scoped module change: one shared `WorkspaceCredentialAdmissionStore` actor and a nonsecret durable denial repository interlocked by a process-shared synchronous transaction gate. Factor the existing Security implementation into a raw synchronous internal primitive; the admission actor must not await the old Keychain actor between checking admission and executing Security. MainActor marker commits and admission-actor Security transactions acquire this same gate. No network, actor hop or suspension is permitted while holding it. It owns exact-scope generation tickets. `loadIfAdmitted`, `saveIfAdmitted`, `denyAndRemove`, and `beginExplicitEnrollment` execute checks, expected-state comparison and synchronous Security operations while holding that shared gate. The gate owns scope generations and expected credential/session identity as well as denial state; MainActor commits its generation change and durable denial under the gate before scheduling actor cleanup. Linearization is successful gated marker commit for denial and successful gated Security write for save; an already-running save may finish before denial, after which denial blocks restoration and its matching removal follows. Marker-persistence failure leaves the process gate denied and an honest unavailable state, rather than publishing durable success. Generation tickets/CAS apply to every load/save/deny/remove/marker-clear, including stale401 cleanup. Destructive operations require exact current generation, expected denial generation and expected credential/session identity; stale operations perform no Security or marker mutation. No callback may erase a newer session or reassert an older denial. Underlying unfenced store must not be reachable from production coordinator callers. Every account/profile uses the same shared admission store; creating another wrapper cannot bypass denial. No global Keychain service clearing.

Before any revocation awaits, MainActor increments matching account generations, cancels provisional matching attempts, invalidates every matching cloud registry handle/ticket, clears receipts/read results and publishes signed-out locally. It synchronously commits a bounded atomic nonsecret denial record for exact origin/profile/account, using an injected owned support-root repository. Then it schedules the shared store denial/removal. If marker persistence fails, publish `localSignOutPersistenceUnavailable`, disable cloud access and retry; do not claim durable logout. Cold launch with unreadable/malformed denial state disables cloud restoration globally for that deployment until repaired explicitly; never treat it as absent.

Denial marker records schema, exact scope and denial generation/reason only; no token, proof, receipt or user text. Use descriptor-owned paths, no symbolic ancestors/final files, bounded regular-file reads and atomic private writes; retain until an explicit successful enrollment replaces denial under matching CAS. Cap records; capacity failure denies new cloud enrollment rather than evicting old denials. This file is device-local support metadata, never exported with a document.

Queued old save before denial may finish first, but subsequent deny/remove wins. Old save after denial fails admission. Old deny/remove queued before a fresh verified same-scope enrollment must fail its generation/credential CAS after that enrollment commits; old marker-clear after a new denial likewise fails. A current-session401 callback carries its captured admission ticket and expected session identity and cannot remove a reauthenticated token. A Keychain remove failure leaves durable denial and blocks reload after restart. Explicit reauthentication uses a new ticket; only a successfully verified enrollment and matching save may clear the marker. Marker-clear failure leaves cloud unavailable and cleans up the newly issued session honestly. No cross-process authority is claimed; app extensions must not write these credentials until a separately designed shared-container locking contract exists.

## Flows and late callbacks

Restore: load exact owned binding, require deployment/profile match and no local denial, obtain the exact account credential through admission store, construct identity actor, call `currentSession()`, then recheck every captured generation and locator before admission. Server account/session readback must match. Any malformed binding, locked Keychain, unknown network or expired/revoked credential yields an explicit unavailable/signed-out state, with local documents intact. A late successful GET or stale401 cannot affect a newer login or another account.

Sign-in: create provisional attempt and challenge on one identity actor; acquire Apple proof in the requesting scene; enroll on that same actor. Check attempt cancellation/generation after each suspension. Once enrollment identifies account, capture/create its exact account slot and credential ticket, reject attempts fenced by intervening logout, save through admitted store, then publish login only after store success and final MainActor checks. If a post-enrollment App fence rejects a credential already returned by the client, use an explicit bounded targeted session cleanup API coordinated in the module: existing automatic discarded-enrollment cleanup covers client-internal cancellation only. Never publish first and repair later. Account identity obtained from verified enrollment does not select a library automatically.

Logout-all: synchronously fence all matching scenes/accounts and persist denial; invoke initiating identity actor's `logoutAll()` without preceding actor invalidation, while other actors are invalidated and all data clients are fenced. Remove exact credentials through shared store. Report local removal and remote confirmed/unknown independently. Single-device sign-out needs a public targeted identity-session logout method or equivalent existing client method after API review; do not substitute logout-all silently.

Deletion: explicit native confirmation explains that owned/shared libraries are retained by current server contract and local documents remain. Acquire fresh enrollment receipt for the same exact account, memory-only, at most the client's conservative five-minute monotonic lifetime. Fence/persist denial before account-delete network; invoke client deletion without pre-invalidating its captured credential. Unknown result remains signed-out and is never presented as confirmed deletion. A retry requires fresh authorization; receipt is one-use. Apple credential-revoked notifications follow the same local fencing and honest remote-revocation path.

Scene closure/cancellation cancels Apple controller and provisional tasks, consumes attempt once, and rejects late publication. Cancelled parsed enrollment keeps current client's cleanup outcome; transport ambiguity before a valid enrollment response is reported as unknown, not fabricated revocation. Logout while an account-unknown login is in flight conservatively fences matching deployment/profile provisional attempts; known-active account B slots, actors, credentials and markers in the same deployment/profile remain intact, as do unrelated deployments. Only account-unknown provisional attempts in that deployment/profile are conservatively cancelled; known attempts matching another account are not invalidated.
