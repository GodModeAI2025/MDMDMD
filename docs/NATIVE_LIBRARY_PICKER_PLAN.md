# Native cloud-library selection and binding

Base: `760dd8c0700e4fe26e60d24beb13a29f73ba5c59`. Depends on the integrated, signed-fixture-verified discovery contract. This stage makes existing remote libraries selectable in the actual account inspector. It does not complete R08 or claim synchronization, key provisioning, narrow-resource shares or collaboration. Creating the first remote library remains required subsequent work; an empty listing must explain that no selectable library exists rather than offer a fake action.

## Current code constraints

The production identity driver saves an actual credential-admission ticket after enrollment, but a restored driver currently receives only a credential. A presentation `.active` value is not sufficient permission to perform metadata requests. The admission context has no narrow public operation for checking an opaque credential against an existing ticket without loading a credential back into app code. The connection registry already provides bounded pending tickets and synchronous owned-repository CAS; its handles are weak and must be retained by the runtime while in use.

## Acceptance

- NP01: Only an acknowledged, currently active exact origin/profile/account session can list or read remote libraries. The real driver checks its durable credential-admission ticket and actual credential before requests and after every await; restored and freshly enrolled drivers both use the real ticket. No Keychain enumeration, default account, synthetic verified DTO or credential getter is added.
- NP02: A request is tied to the current window, library facade, owned locator, account slot generation and driver incarnation. Logout, deletion, facade replacement, detach and explicit cancellation prevent late results from updating the picker or binding. Unrelated account/window requests remain usable.
- NP03: The actual inspector presents at most eight rows at a time, a bounded cursor history, empty/error/retry states and explicit selection. Metadata is escaped native text, not executable instructions. No arbitrary UUID input or automatic first-row selection.
- NP04: Selecting a row issues a fresh authenticated metadata read for that exact UUID. Role/session changes, malformed responses, stale requests or lost local admission prevent persistence. A listing is not ongoing permission authority.
- NP05: Persistence uses the actual owned `CloudLibraryBindingRepository` and existing registry ticket/CAS. Record exact origin/profile/account/remote-library ID. Validate request/admission immediately before the synchronous save; retain the resulting handle. Competing selections and changed on-disk bindings fail explicitly rather than overwrite each other. Binding metadata does not authorize later server requests.
- NP06: Library documents, revisions, images, byte content and unrelated bindings remain unchanged. A successful association is described as an association, with an explicit statement that it alone does not upload/synchronize documents. It does not imply possession of an encryption key.
- NP07: Model/UI outcomes are controlled and nonsecret, synchronize other windows using the same owned locator, and become invalid/unchecked after exact account invalidation. Fresh native light/dark/max-text/phone/iPad checks cover obtained destinations honestly; missing destinations remain open.

## Interfaces and decisions

1. Add a narrow module admission-context validation operation accepting `WorkspaceCredentialAdmissionTicket` and an opaque `WorkspaceCredential`, returning no credential/authority DTO, plus a trusted synchronous gated commit callback. Under the existing gate, check ticket identity/generation, denial ledger, eligible/admitted state, actual Keychain fingerprint and matching supplied credential fingerprint. Do not hold the gate across network calls. Use validation before and after each request. For final publication, keep the same gate held through the trusted synchronous registry/repository CAS callback. The callback must not await, call network APIs, reenter admission APIs, or publish arbitrary user callbacks. Lock order is admission gate → existing binding repository transaction lock; no caller may hold the repository lock while entering admission. Repository operations currently do not call admission, and the repository caps metadata at 8192 bytes; OS-level I/O is not claimed to have a hard deadline.
2. Add a separate internal `WorkspaceLibraryDiscoveryDriver` protocol for admission adoption, list, exact metadata and admission validation. The real production identity driver conforms. Existing identity-only test drivers cannot perform discovery unless they explicitly conform; their original assertions remain intact. On restore, supply the exact loaded credential/ticket pair to the discovery driver before remote restoration. Newly enrolled drivers retain the verified enrollment credential and actual saved ticket. Neither path derives authority from `.active` presentation.
3. Coordinator request handles are opaque, bounded, memory-only and non-Codable. Capture actual driver identity and slot generation; check exact attached window scope after every suspension. No receipt/session credential is placed in an observable model. Explicit cancellation closes only that request; account logout/deletion fences all matching scope requests before await.
4. Add `WorkspaceLibraryPickerPresentation` with page rows, cursor, busy/status/outcome and selected association display only. Current page has at most eight rows; retain at most sixteen prior cursor positions, dropping oldest history without preventing further forward pagination. Replace page rows rather than accumulating the entire catalog.
5. Runtime methods require captured window ID, owned locator and facade ID. Keep per-owned-locator binding presentation shared across its actual windows, with bounded weak ownership and no lifetime exhaustion. Retain registry handles in actual runtime registrations and clear/reconcile displays when handles are invalidated. Existing metadata restore remains consent-gated.
6. Association flow: capture registration and actual admission → begin registry ticket with the exact current on-disk expected binding → fresh metadata readback → recheck registration/account → gated admission validation plus synchronous registry completion/repository CAS → publish shared association state after the gate returns. Cancel the ticket on every failed/obsolete path. No suspension occurs inside the gated commit. Both validation and disk commit share its linearization: if denial acquires the gate first, no binding is saved; if the binding commit acquires it first, subsequent denial fences further use and runtime account invalidation reconciles the nonauthorizing association display. Absence of MainActor await alone does not prove this cross-executor ordering. A concurrent server revocation after readback still cannot be treated as ongoing permission; future operations must reauthorize.
7. The user chooses **Zuordnen** and confirms the target library. Preserve any existing association until successful CAS replacement. Display conflict/unknown/denied results precisely. Changing associations affects metadata only; data transfer and encryption-key work are separate required activation stages.

Rejected: a UI-owned `WorkspaceClient` built from copied credentials, relying only on displayed active state, trusting a selected list row instead of readback, resolving arbitrary library paths, silently replacing a binding, accumulating all pages, and showing synchronization as active after a metadata save.

During native checks, keep production sources immutable, use actual Xcode MCP and exclusively delegated device sessions, archive obtained screenshots/hierarchies and restore settings/resources.
