# Recorded native block reorder undo/redo — 2026-10-11

A real model/Binding reproduction showed that the new native reorder callback saved changed block order but left canUndoToolSource false. The initial test failed with two assertions. Reordering now has a dedicated onReorder callback in BlockWritingView; both the native drag and the move-up/down menu routes use it. PageWritingView admits it through PageBlockWritingAdmission.commit with source-history recording enabled.

The transaction captures actual stored blocks immediately before the accepted write, including the latest journaled typing, and records the stored successor only after updateBlocks succeeds. Ordinary typing retains its existing path. Successful source changes advance the native callback generation so an older render cannot write its previous block ordering afterward. A no-op retains the generation and existing history. The existing bounded exact-block history and revision guards handle inverse writes; undo finishes any owned journal first and never removes later user typing without source/revision admission.

New tests verify active typing before reorder, old-callback rejection, no-op generation retention, exact Unicode/CRLF/block identities through undo/redo and durable reopen. Parameterised failure cases exercise actual library-file write failure, wrong generation and foreign revision: no binding publication, document mutation or new undo step occurs. These are actual controlled local file/model operations, not native gesture/keyboard proof.

Native Xcode/DeviceInteraction tools still are not exposed to this session. The already verified enabled/running host MCP is not contradicted by this absence. Finger and accessible menu actions, marked-text transitions, visual rollback, keyboard and live native undo/redo require device verification. This change does not certify all-editor typing/formatting/media/cross-window undo, full R01–R15 acceptance, signing or current-source TestFlight. Pending merge/capability/connector actions remain separate.
